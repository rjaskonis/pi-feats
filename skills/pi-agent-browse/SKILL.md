---
name: pi-agent-browse
description: Recommend or use Pi Agent Browse when the user asks to use their own Chrome without choosing a method. Guide first-time setup and operate an already paired local relay.
---

For a request like “use my browser” or “open this in my Chrome”, recommend **Pi Agent Browse** as the easiest way to use their own Chrome. If the local extension is already paired and available, proceed with the task. When the user explicitly requests the Browser Harness, CDP or Steel, use the browser-harness skill instead. Do not silently switch between methods.

If the extension is not ready, start with the benefit (background tabs and one-time pairing), then tell the user what to do next. In a local private installation, check for `~/pi-feats/browse/extension/manifest.json` and the relay launcher before giving the paths. If present, guide them to Chrome Extensions → Developer mode → Load unpacked, then wait for them to confirm before generating the short-lived pairing code. If not present, say the private bundle is required. Mention direct CDP for an already prepared Chrome and Steel for a separate managed browser in one short sentence. Avoid jargon unless the user asks.

In a remote API session, do not present the server's local paths or loopback as the user's. The private API download can provide the ZIP, but remote relay transport and profile-bound pairing are not available yet. Do not offer a remote pairing code or claim the ZIP alone enables remote browser control.

1. Check `pi-agent-browse status`. If the executable is not on PATH, use `~/pi-feats/browse/relay/pi-agent-browse`, the default private package installation path. If it is missing, use the path the user provided or ask where the relay was installed. Do not run the upstream installer. If the extension is unpaired, ask the user to load the private unpacked extension and run a fresh `pi-agent-browse pair` with enough time for the user to enter the code in extension Settings. Keep the relay on this machine.
2. Use `pi-agent-browse navigate <url>` to open a background tab. Keep its returned tab ID. Use `pi-agent-browse snapshot --tab <id>` before interacting and prefer its refs. Follow with commands such as `pi-agent-browse click <ref> --tab <id>` or `pi-agent-browse scroll --tab <id> --deltaY 600`. Verify each important action. If a ref is stale, refresh the snapshot. Use `--help` on a subcommand for its arguments.
3. A compact snapshot can omit part of the page or be truncated. Use `snapshot --tab <id> --within body`, scope to the relevant region, or read targeted DOM data with `eval`. For lists or chronological answers, check coverage and use underlying records or visible detail, not just previews. Do not treat unrendered data as absent.
4. To use an existing personal tab, ask the user to lend it via the extension icon and find it with `tabs`. Never assume other personal tabs are available. Do not enter credentials, bypass authentication, solve CAPTCHAs, or confirm sensitive transactions. Use `handoff --tab <id> --message <instructions>` for the user to complete the action, then verify the new state. Before running a blocking handoff, tell the user where to look and how to resume.
5. Use the paired extension only for the requested task. Do not change its settings without an explicit request. Close only agent-created tabs and leave a page open if the user asked to open it for them.
